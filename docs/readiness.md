# Проверка готовности JanaMen

Перед показом выполните `npm ci`, `npm run lint`, `npm test`, `npm run build` и `npm run test:smoke`. Для Python-оценщика нужны `npm run eval:validate` и `npm run eval:self-test`; если команда Python называется иначе, задайте переменную `PYTHON`. Эти проверки не подтверждают качество настоящей модели. Для отдельного измерения установленного движка используется `npm run ai:check`.

## Сквозные сценарии

Используйте разные браузеры или профили для сотрудника, руководителя и HR. Обычные вкладки разделяют сессию.

1. Сотрудник создаёт отпуск, видит резерв дней и следующего согласующего. Повторное нажатие не должно создавать второй отпуск.
2. Руководитель открывает заявку из очереди на главной странице и согласует её. Заявка исчезает из его очереди и появляется у HR.
3. HR подтверждает отпуск. Сотрудник получает уведомление, видит списание дней и открывает печатное заявление.
4. Для отдельной заявки проверьте отказ с причиной и отмену автором. Резерв должен освобождаться.
5. Сотрудник проходит уроки и тест назначенного курса. Прогресс сохраняется после повторного входа; руководитель и HR видят результат в очереди обучения.
6. В чате задайте вопрос о подаче отпуска, затем о переносе на следующий год. Для второго вопроса в БЗ нет правила: требуется отказ с предложением обратиться к HR.
7. Передайте вопрос HR, ответьте от HR и откройте уведомление сотрудника. В обращении должны оставаться исходный вопрос, ответ и имя специалиста.

## Доступ и восстановление

Обычный сотрудник не изменяет кадровые поля, руководитель не согласует себя, HR не читает записи другой компании. Изменённый в адресе ID не должен обходить проверку прав. Автотесты проверяют чужие профили, вложения, курсы, заявки и mock-документы.

При потере соединения интерфейс сохраняет последнее состояние и сообщает, что данные требуют обновления. После подтверждённой записи ошибка последующего чтения не должна предлагать повторно создавать заявку. Проверяйте это отдельно от обычного успешного пути.

## Интерфейс

Проверьте вход, форму отпуска, обучение и чат на узком экране, длинные ФИО и казахские тексты. Кнопки должны оставаться доступны с открытой клавиатурой. Переключение языка не должно сбрасывать текущую заявку. Системные предпочтения и особенности мобильного браузера могут влиять на внешний вид.

## Границы результата

Очередь показывает фактическое время ожидания и реальные назначения из доступных данных; SLA и нормативные сроки не заданы. Проверка фактов ассистента консервативна и может отклонить новую формулировку. Регрессионные вопросы входят в исходники и не являются независимой приёмочной выборкой. Казахские тексты требуют проверки носителем языка. Интеграции остаются mock API, а кадровые правила — вымышленными.

- В браузере на 390×844 и обычном экране проверено обучение на казахском: переход к первому непройденному уроку, запрет теста до уроков, сохранение двух выбранных ответов при закрытии/открытии, обратная связь после 0%, успешная пересдача до 100%, сохранение результата после перезагрузки. Горизонтального переполнения диалога нет; ошибок консоли нет. Также исправлено влияние старого глобального CSS на сообщения статуса в тёмной теме.

Итоговый максимум — 4,87 с, p95 RU/KK/EN — 2,20/4,51/1,21 с на Intel i7-1065G7 с двумя потоками модели. Все 288 проверок оригиналов источников (3 языка, 4 роли, JSON/HTML) прошли. При отсутствии модели работает поиск по подтверждённым фактам; контролируемое зависание заканчивается таким же ответом через 8,01 с. Результаты сохраняются в `evaluation/runs/2026-10-18-*`; окончательный прогон — `2026-10-18-final-product`, вместе с SHA-256 вопросов и проверенного кода.

54 вопроса использованы при исправлении словаря и теперь являются регрессией. Повторный прогон не делает их независимой выборкой. Для обоснованной претензии на максимальные баллы остаются внешняя проверка по фактической рубрике организаторов, новые вопросы от человека, который не менял код, и проверка казахского текста носителем. Эти действия нельзя заменить количеством автотестов или автоматически выставленной оценкой 95/95.

## Приёмка после исправления Documentolog и приветствий

- События документооборота отделены от согласования отпуска, в том числе у ранее сохранённых уведомлений. Чтение истории документа не помечает одобрение отпуска прочитанным. При одинаковом времени событий отображается наиболее поздний этап обработки.
- Автор, его руководитель и HR своей компании читают только статус и историю документа. Исходный интеграционный payload и внутренние ID участников не выдаются. Менять статус может только HR; чужая компания получает 404. Отказ Documentolog не меняет согласованный отпуск и баланс дней. История переживает перезапуск и остаётся доступной при отключении mock-операций.
- В браузере сотрудник открыл Documentolog из уведомления, перешёл в заявку и вернулся к документу. Проверены RU/KK, ширины 826 и 390: нет горизонтального переполнения, кнопки внизу диалога доступны при прокрутке. Это проверка интерфейса, а не экспертная лингвистическая приёмка перевода.
- Переносимая сборка в чистой папке дополнительно проверяет регистрацию → рассмотрение → отклонение документа, права сотрудника и отдельный статус согласованного отпуска.
- На новых внутренних вопросах обнаружены пять ложных отказов из-за приветствий RU/KK/EN. Исправлено распознавание только начального приветствия и вежливых слов; неподтверждённые условия по-прежнему запрещены. 14 новых регрессионных тестов проверяют известные вопросы, неизвестные условия, чужие данные и попытку изменить инструкции.
- [Прогон работающей локальной модели](../evaluation/runs/2026-10-18-documentolog-greetings/summary.json): прежний корпус 54 вопроса × 2, 108/108; новые формулировки — 12/12 после исправления (до исправления 7/12). В прежнем корпусе 60 ответов с выбором источника моделью и 48 отказов, без резервного режима; максимальная наблюдённая задержка 5,206 с. Это внутренний прогон на работающем движке, не независимая проверка качества и не измерение холодного старта. В отчёте сохранены вопросы, ответы и хеши проверенного кода.

Функциональные проверки по ТЗ закрыты внутренними тестами и ручным проходом. Независимое прохождение незнакомым пользователем и проверка казахского носителем остаются неподтверждёнными; это явные условия внешней приёмки, а не реализуемые программой функции.
