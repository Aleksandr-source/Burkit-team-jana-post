# Доступ к базе знаний и ответы с источниками — предложение для JanaMen

Статус: проект решения, не внедрено в исходники. Основание: текущие server/knowledge.mjs, server/assistant.mjs, результаты отдельных экспериментов и требования C07/C12 из предоставленной спецификации. Правила текущей базы демонстрационные. Прямое соответствие оригинальному клиентскому DOCX не перепроверено: исходный DOCX в этой задаче не предоставлен.

## Что нужно обеспечить

Пользователь задаёт вопрос своими словами на RU или KK. Сервис отвечает только подтверждёнными доступными сведениями, показывает конкретный источник и прямо сообщает, каких сведений не хватает. Понимание перефразировок не должно расширять права и не даёт права восполнять отсутствующие факты.

Полный текст цитаты и правильный документ — разные проверки. Подлинная цитата про продолжительность отпуска не отвечает на вопрос о сроке подачи заявки. Нельзя считать наличие ссылки достаточным доказательством правильности.

## Предлагаемая цепочка

1. **Идентификация и разрешения на сервере.** User/role/company/team приходят из проверенной сессии, а не из вопроса или тела запроса. Фильтрация прав, версии и срока действия источника выполняется ДО поиска, ранжирования, кеширования и отправки модели. Модель не получает список закрытых документов и не определяет свои права. Текущая база имеет только audience; company/team/validity — поля для последующего расширения, а не реализованные возможности.
2. **Представление базы.** Хранить полный оригинал документа и небольшие смысловые фрагменты: заголовок, условия, правило и исключения вместе. Не обрезать по первым 35 символам. Для каждого фрагмента: document_id, fragment_id, version, language, content_hash и точные символьные смещения либо ID предложений. Русский и казахский варианты одного правила связывать общим rule_id, проверять смысловое соответствие. Не считать дату документа достаточной гарантией актуальности.
3. **Поиск смысла вопроса.** Для нынешних 11 документов сначала сравнить простой поиск по всему разрешённому набору и ранжирование по словам/вариантам формулировок. Сохранить русские и казахские синонимы, отрицания, статусы и даты. Для роста базы отдельно испытать мультиязычный семантический поиск вместе с лексическим; конкретный embedding пока не выбран и не измерен. Расширение запроса служит только поиску, не становится источником ответа.
4. **Достаточные кандидаты.** Передавать завершённые смысловые фрагменты с ID и условиями. Число и размер кандидатов определять по реальному токенному бюджету, а не фиксированным символам. Не обрезать важное исключение. При превышении контекста ранжировать/разбивать проверку на этапы. Сохранять трассу: какие кандидаты были доступны и почему выбраны.
5. **Проверка ответа на конкретный вопрос.** Разделить составной вопрос на запрошенные факты. Для каждого: подтверждён ли он в доступном фрагменте? Результат селектора — ID доказательства или insufficient; никакого собственного кадрового правила. Обнаруженный конфликт источников, недостаток условия или неясный вопрос переводят ответ в clarification/insufficient. Самооценку уверенности модели не считать доказательством.
6. **Проверка результата сервером.** ID должен принадлежать разрешённому набору этого запроса; версия/hash совпадать; выбранная цитата существовать дословно. Проверять структуру ответа, допустимые ID и не принимать произвольные URL. Эти проверки гарантируют происхождение, но сами по себе не доказывают смысловую релевантность — её проверяют отдельным тестом и, при необходимости, вторым этапом оценки достаточности.
7. **Стандартизированное представление.** На первом этапе использовать локализованный шаблон + проверенный точный фрагмент. Вариативность вопроса обеспечивается поиском и выбором, а не сочинением правил. Генеративное перефразирование включать отдельным экспериментом лишь после проверки всех утверждений и чисел; сейчас оно не требуется для демонстрации источников.
8. **Переход к источнику.** Сервер собирает ссылку из document_id/version/fragment_id, UI открывает документ и подсвечивает подтверждающий фрагмент. Обработчик просмотра повторно проверяет актуальные права — даже для скопированной ссылки. Данный endpoint предстоит реализовать; произвольную придуманную ссылку нельзя выдавать как существующую.

## Контракт ответа

Предлагаемый ответ сервера:

```json
{
  "status": "answered",
  "language": "ru",
  "answer": "По демонстрационным правилам: … [1]",
  "claims": [{"text": "…", "evidence_ids": ["leave-decisions@DEMO:sentence-4"]}],
  "sources": [{"document_id": "leave-decisions", "version": "DEMO · 16.10.2026", "fragment_id": "sentence-4", "title": "Согласование, отказ и отмена", "quote": "Сотрудник может отменить свою заявку до окончательного одобрения HR.", "content_hash": "<вычисляет сервер>", "locator": {"document_id": "leave-decisions", "fragment_id": "sentence-4"}}],
  "unanswered_parts": [],
  "trace_id": "<идентификатор замера>"
}
```

Это эскиз контракта, а не формат уже работающего API. Модель возвращает только ID/статус; quote/hash/title/locator восстанавливает сервер. До внедрения обработчика источника locator не отображается как работающая ссылка.

Статусы: answered, partial, insufficient_evidence, clarification_required. При технической ошибке — отдельный service_unavailable: сбой сервера нельзя выдавать за отсутствие сведений в базе.

## Формулировки отказов и частичных ответов

- RU: «В доступной мне базе знаний нет подтверждённых данных по этому вопросу. Уточните вопрос или обратитесь в HR.»
- KK: «Маған қолжетімді білім базасында бұл сұраққа қатысты расталған дерек жоқ. Сұрақты нақтылаңыз немесе HR маманына хабарласыңыз.»
- Составной вопрос: ответить на подтверждённую часть с источником, отдельно назвать часть, для которой данных нет. Не замалчивать вторую половину.
- Неоднозначность: задать один уточняющий вопрос (например, об этапе заявки), если именно этого условия не хватает. Не спрашивать персональные данные, не нужные для общего правила.
- Ограничение доступа: нейтральное отсутствие доступного подтверждения; не раскрывать существование, название и содержание закрытых документов.
- Просьба выполнить кадровое действие: сообщить об ограничении действий и, при наличии подтверждённой инструкции, объяснить самостоятельный путь.

Собственный баланс — отдельная серверная функция чтения доверенного контекста. Ссылка на общую статью не является источником персонального числа. При дальнейшем включении значений нужен отдельный разрешённый provenance-тип для записи кабинета, без выдачи внутреннего идентификатора чужой записи.

## Лимит времени

10 секунд — внешний бюджет полного ответа, а не только max_tokens. Предлагаемая точка отсечения вызова модели 8 секунд оставляет бюджет на поиск/проверку/доставку; это инженерный параметр, который надо измерить, а не обещание. Отмена upstream-запроса должна освобождать ресурс, очередь ограничена. Если подтверждённый результат не получен вовремя, вернуть технический статус; нельзя молча подменять модель выдачей первого фрагмента. Разрешённый резервный поиск маркировать и оценивать отдельно.

Кеш разделять по области доступа, языку, версии базы и нормализованному вопросу; сбрасывать при изменении правил/прав. Логи не должны содержать токены сессии, runtime-key и лишние персональные данные.

## Приёмочные проверки до интеграции

- Перефразировки RU/KK, опечатки, отрицание, неверные предпосылки, составные вопросы.
- Полные фрагменты; правильное доказательство на разных позициях; оба кандидата нерелевантны; нужный источник отсутствует в retrieval.
- Отдельно retrieval recall, точность выбора, полнота покрытия запрошенных фактов, доля верных отказов, ложные ответы на неизвестное, корректность цитат и доступа.
- Каждый факт имеет существующее доказательство. Сам факт существования документа не даёт балл за релевантность.
- Запрос сотрудника не читает HR-источник; прямой URL источника проверяется сервером; текст «я HR» ничего не меняет.
- Конфликт/устаревание/обновление источника, prompt injection внутри вопроса и документа.
- p50/p95/max полного HTTP-ответа, холодный запуск и конкурентная нагрузка; отдельно fallback/model/error.
- Положительные сценарии аванса добавлять только после утверждения соответствующих правил. Сейчас возможны только корректные отказы.

## Порядок внедрения после отдельного разрешения на исходники

Сначала — контракт источников и проверки прав, затем эталоны/полные фрагменты, поиск и измерение recall, затем достаточность и селектор, затем UI-ссылка и HTTP-проверки. Использовать только конфигурацию, прошедшую отложенный набор и проверки отказов. Если закреплённая модель не проходит, честно оставить её экспериментальной и сравнить иной подход/модель; не компенсировать недостаток качества неподтверждёнными ответами.
